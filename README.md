# CivicLens frontend

A local, dependency-free frontend based on `features.md`, `initial-unfinalized-plans.md`, and the three references in `UI-photos/`. Navy surfaces, cyan navigation, category-colored map markers, dashboard charts, and a synchronized issue table follow the references.

## Run

With Node.js 18 or newer:

```sh
npm run dev
```

Open http://127.0.0.1:5173. No installation or build step is required. Without Node, serve the repository with any static HTTP server, for example `python -m http.server 5173`. ES modules require HTTP; opening `index.html` directly is not supported.

## Plug in your data

`data-contract.md` documents the issue shape, the submission draft and the infrastructure format.

1. Run `python -m analysis --input <photo analysis output>` (see `analysis/README.md`). `issueRepository.list()` loads the resulting `data/analyzed/issues.public.json`, which follows `data-contract.md`, and uses the frontend's neighbourhoods, wards and infrastructure (exported with `node scripts/export-analysis-reference.mjs`). Later, replace `issueRepository.list()` with a request to your API. Without analysis output it returns 240 deterministic, fictional records spread over the 90 days before the fixed demo date (**October 17, 2026**), with a sample rainstorm on Oct 4–6 so the timeline has a real event in it. Every record has `is_demo: true`.
2. Replace `issueRepository.submit(draft)` with your submission endpoint. The current implementation saves metadata in browser local storage (pin rounded to about 100 m) and previews photos in memory only. Real photo transport, privacy processing, review, authentication, and publication belong on the backend.
3. Set `evidence_thumbnail` to a privacy-processed image URL. Until then, each issue shows a credited sample photo of its category from `assets/evidence/` (CC BY / CC BY-SA, see `assets/evidence/CREDITS.md`), labelled as a sample that does not depict the record.
4. `src/map.js` is the isolated map adapter. It renders real OpenStreetMap raster tiles styled for the dark interface with no API key, geographic markers, pixel-based clusters, panning, cursor-anchored eased zoom, pinch zoom, double-click zoom, gentle pan momentum, Shift selection and box selection. Camera animation reuses the current tile scene until destination tiles are ready, and respects reduced-motion preferences. It can be replaced by MapLibre while preserving callbacks. Network access is required for tiles and optional fonts; an explicitly labeled schematic background and system fonts remain available offline.
5. Infrastructure layers use real OpenStreetMap geometry for TTC subway/LRT stations and four major roads (`src/osm-infrastructure.js`, regenerated by `python scripts/fetch-osm-infrastructure.py`). School positions are an approximate sample list.

## Implemented interactions

- **Map Explorer** uses a compact title and floating search / filter controls over the expanded map. It opens without a context panel. Pins open details; clusters open a sortable/filterable list without auto-zoom. Zoom in is explicit. Shift + click toggles issue IDs; Box select (dashed square) makes a rectangular selection; ordinary drag pans. Escape or blank-map click clears selection. High-severity pins and clusters carry a "!" badge, so severity never depends on colour alone. The selected pin is moved clear of the side panel or phone bottom sheet. Markers have contextual hover / focus previews; a single selected issue shows its uncertainty area. Fit all matching issues, keyboard map controls, and empty-result recovery are supported.
- **Issue details** show the evidence photo, a "How this location was estimated" trace (method, cascade steps, visual clues, radius and confidence; illustrative until the geolocation pipeline is connected), ward, last seen, nearby infrastructure and why it was flagged.
- **Shared filters** (search, issue type, severity, status, time, ward or neighbourhood, and infrastructure proximity) apply across map, table, and dashboard. Proximity works for one asset type or "any infrastructure". Filter chips can be removed individually. Search suggestions jump to matching issues, neighbourhoods and wards; no external geocoder is connected.
- **Data Explorer** defaults to all filtered Toronto records. View as table explicitly carries selected IDs with a removable scope chip. Columns cover area and ward, location with nearest asset, detected, last seen, sightings, confidence, source and verification; they sort (including semantic severity ordering). Sticky headers, selection actions, pagination, per-page sizes, map navigation, and CSV / GeoJSON downloads work. The **Query** tab shows the active filters, scope, sort and page as a read-only SQL statement plus the issue schema. Escape clears the table selection.
- **Dashboard** cards, timeline (daily up to 30 days, weekly beyond), category bars, resolution chart and hotspots derive from the same filtered sample records. With a 7- or 30-day filter, cards compare against the previous period of the same length computed from the data; no invented growth. The **ward digest** summarizes one of the 25 wards from the filtered records with a fixed, labelled template and counts down to the October 26 municipal election. The **pipeline funnel** shows sample ingestion metrics (labelled as such) followed by detected and verified counts from the dataset.
- **Upload** supports up to 3 JPEG / PNG / WebP photos, size validation, previews, removal, a drag-the-map pin picker limited to Toronto, nearest address, review, and a local receipt. Your submissions then appear under Saved.
- Saved bookmarks, recents, preferences, and pending submission metadata persist in this browser. The demo role selector (sidebar, or Settings on a phone) shows a sample volunteer review queue. Review decisions last for the session. It is **not authentication**. Mapillary is a visibly unconnected integration placeholder; dragging the person opens it rather than fabricated coverage.
- On phones the sidebar becomes a bottom tab bar, and the map supports pinch zoom.

## Limits and production integration

The public demo uses coarse fictional coordinates. CSV omits coordinates; GeoJSON exports approximate uncertainty areas with a minimum 250m radius. Authorization and coordinate precision must be enforced on a real backend, including exports, rather than trusted to this client. Ward assignments in the sample are approximate (one ward per neighbourhood). Ingestion funnel numbers, geolocation traces and explanations are illustrative. No actual AI, scraping, 311 requests, location lookup, Mapillary imagery, correction-pin workflow, or saved query builder is connected. There is no paid service or API key configured.
